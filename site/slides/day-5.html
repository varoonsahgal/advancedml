From autocomplete to reasoner

SFT, LoRA, DPO, and RL with verifiable rewards: the post-training stack.

The art is real: 36 toy GRPO runs (tabular policies, binary verifiable reward). Each honey line is a run's accuracy; the cream line is the mean. You'll make a real version of this curve in Lab 5.2.
The life of an LLM

Pretraining buys knowledge. Post-training buys behaviour.

Walk left to right. Knowledge mostly comes from pretraining; everything after shapes behaviour. Ask: which stage would you change to teach the model a new fact? (Trick: usually none. Use RAG. That's myth #1 later.)
LoRA · Hu et al. 2021

Learn a low-rank update

$$h = W_0x + \tfrac{\alpha}{r}\,BAx$$
  • Freeze $W_0$. Train only the thin $B$ and $A$.
  • $B=0$ at init: step 0 is the base model.
  • Merge $W_0+\tfrac{\alpha}{r}BA$ after: zero latency.
  • QLoRA: keep the frozen base in 4-bit NF4.
Fine-tuning updates have low intrinsic rank, so r = 8–64 often comes close to full fine-tuning. Full FT also needs ~16 bytes of optimizer state per parameter. Ask: why init B to zero rather than A? (So BA = 0 but gradients still flow into B, because A is random.) The 65,536 number shows up again in the Lab 5.3 agent trace.
🍯 Key takeaway

Fine-tuning updates are low-rank. Train a 0.4% sliver, then merge it for free.

The real levers: rank, which modules you target, and above all data quality. For new facts, reach for RAG instead.

Preference tuning · DPO

Preferences, without the RL loop

Demonstrations teach format. Preferences ("A beats B") teach judgment.

$$-\log\sigma\Big(\beta\log\tfrac{\pi_\theta(y_w)}{\pi_\text{ref}(y_w)}-\beta\log\tfrac{\pi_\theta(y_l)}{\pi_\text{ref}(y_l)}\Big)$$
  • No reward model, no PPO: a classification-style loss.
  • $\pi_\text{ref}$ and $\beta$ act as an implicit KL anchor.
Classic RLHF: train a reward model on comparisons, then PPO with a KL penalty to the SFT model. DPO (Rafailov et al., 2023) notices the optimal policy implies a reward, so you can train straight on pairs. Each log-ratio is an implicit reward; the loss is a logistic loss on their difference. You implement this with a checkpoint in Lab 5.2.
GRPO · Shao et al. 2024

Grade each answer on a curve

$$\hat A_i \;=\; \frac{r_i-\operatorname{mean}(r_1,\dots,r_G)}{\operatorname{std}(r_1,\dots,r_G)}$$
rᵢA verifiable reward: does the answer check out? (+ format)
GA group of answers sampled for the same prompt.
mean, stdThe group is its own baseline: no critic network.
+ clip, KLPPO-style ratio clipping and a KL to πref keep steps small.
Full objective: average over the group and tokens of min(ρ·Â, clip(ρ, 1±ε)·Â), minus β·KL to the reference. ρ = π_θ/π_θold. PPO needs a value network the size of the policy to estimate a baseline; GRPO replaces it with the group's mean. That's a huge memory saving for LLMs.
RL with verifiable rewards

Push up answers that beat their siblings

  • Every token of a +Â answer goes up; every token of a −Â answer goes down.
  • DeepSeek-R1 (2025): simple correctness + format rewards → long, self-correcting reasoning.
  • All-right or all-wrong group → zero signal. Tune difficulty.
Reward hacking is real. Strict verifiers, a KL anchor, and read your samples.
The bottom panel is why curricula and difficulty filtering matter: with G = 8, a prompt the model solves 95% of the time teaches nothing two-thirds of the time. Reward hacking examples: formatting tricks, editing the unit tests, answers that game a lenient parser. Watch for "reward up, quality down".
🍯 Key takeaway

No critic, no reward model: the group is the baseline.

A reward you can verify plus group-relative advantages gave us reasoning models. Keep prompts hard enough that the group disagrees.

13:15 · Test-time compute

Thinking longer: a second scaling axis

Monte Carlo, 400 simulated problems: a perfect verifier keeps climbing; voting stalls.
Afternoon lecture starts here. Besides a bigger model or more training, spend compute at inference: longer chains of thought, self-consistency voting, best-of-N against a verifier. pass@k = 1 − (1 − p)^k per problem. That's why math and code (checkable) improved fastest. Snell et al. 2024: optimally spent test-time compute can beat a bigger model.
Quiz · test-time compute

Why does voting stall near 62% while pass@k reaches 99%?

Voting needs far more than 256 samples
On ~38% of problems a wrong answer is likelier than the right one
The verifier is noisy
The sampling temperature was too low

B. Voting amplifies the plurality, so it locks in a dominant wrong answer. pass@k only needs one right sample and a checker to spot it.

Show of hands, then reveal. Follow-up: when does voting actively hurt compared with a single sample? (When one specific wrong answer beats the right one: majority converges on it.)
02

Agents: LLMs that act

A loop, some tools, a protocol, and the evals that prove it works.

The art: the cosine-similarity matrix of the retrieval corpus we use in two slides, sorted by topic. Bright blocks are topics; retrieval lives inside those blocks.
The agent loop

An agent is an LLM in a loop

  • The model emits a structured tool request.
  • Your code runs the tool.
  • The result goes back into the context.
  • Repeat until there's no tool call, or the turn budget runs out.
Key point: the model never runs anything. It emits JSON; your code executes it; the output is just more text in the context. That's also why prompt injection works, which we'll see shortly. ReAct (Yao et al., 2023) is this loop with explicit reasoning between actions.
The whole agent

No framework required: 13 lines

def run_agent(llm, tools, user_msg, max_turns=10):
    messages = [{"role": "user", "content": user_msg}]
    by_name = {t.name: t for t in tools}
    for _ in range(max_turns):
        reply = llm(messages, tools=[t.schema for t in tools])   # model may request tools
        messages.append({"role": "assistant", "content": reply.content})
        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:
            return reply.text                                    # done: final answer
        results = [{"type": "tool_result", "tool_use_id": c.id,
                    "content": str(by_name[c.name](**c.input))} for c in calls]
        messages.append({"role": "user", "content": results})    # observations go back in
    raise RuntimeError("agent ran out of turns")
Walk the loop: messages list is the agent's memory; tool schemas tell the model what it may call; tool_use blocks are requests; tool_result blocks are observations. In Lab 5.3 this runs against the Claude API, or a mock LLM offline. Spend effort on tools, traces, evals and guardrails, not on frameworks.
RAG · retrieval-augmented generation

Ground answers in your data

  1. Chunk documents and embed them.
  2. Retrieve the top-k chunks by cosine similarity.
  3. Put them in the prompt, and cite them.
Most RAG failures are retrieval failures. Measure recall@k first.
The third hit is a genuine failure of a weak embedding: lexical overlap on "adds". Dense embeddings and a reranker would fix it, but you only notice if you measure. Ask: what's the cheapest way to measure recall@k? (Write 20 questions with known source chunks.)
MCP · Model Context Protocol

USB-C for AI tools: write the server once

from mcp.server.mcpserver import MCPServer
# mcp 1.x: from mcp.server.fastmcp import FastMCP

mcp = MCPServer("hive-tools")

@mcp.tool()
def honey_yield(hives: int, kg: float = 25.0) -> float:
    """Estimate a season's honey yield in kg."""
    return hives * kg

if __name__ == "__main__":
    mcp.run()   # stdio: any MCP client can call it
Introduced by Anthropic in late 2024, now an open standard across the industry. The host (an IDE, a chat app, your agent) runs one client per server. The server declares tools from type hints and docstrings. Quiz-in-passing: who executes the tool? The MCP server; the client forwards the model's request and returns the result. On SDK 1.x the import is FastMCP; the rest is identical.

Evals

“It looked good on five examples” is not an eval

✅

Code-graded

Exact match, unit tests, JSON schema, numeric tolerance. Cheap, deterministic, trustworthy.

🧑‍⚖️

Model-graded

An LLM judge with a rubric. Calibrate it against humans; watch position, length and self-preference bias.

👀

Human review

The ground truth, and expensive. Use it to build and audit the other two.

🐝 Public benchmarks saturate and leak into training data. The eval that matters is built from your users' real tasks.
Every serious LLM project needs a fixed set of realistic inputs, automatic checks where possible, and a score you track on every prompt, model or retrieval change. Capstone teams: your rubric gives 25 points for evaluation rigor.
🍯 Key takeaway

Write the eval before you optimize. Then read your failures every week.

Code-graded where you can, model-graded where you must, and humans to keep both honest.

What is the model thinking?

Superposition, sparse autoencoders, and steering.

The art is a trained toy model (Elhage et al., 2022): 6 sparse features squeezed into 2 dimensions. Gradient descent arranges them as a hexagon, the most orthogonal packing it can find. Yes, the model literally discovered the honeycomb. 🐝
Sparse autoencoders

Un-mixing superposition

Models pack more features than dimensions, so single neurons are polysemantic.

$$\begin{gathered}f=\mathrm{ReLU}\big(W_e(x-b_d)+b_e\big)\\ \hat x = W_d f + b_d\\ \mathcal L=\|x-\hat x\|^2+\lambda\|f\|_1\end{gathered}$$
  • Dictionary 16–64× wider than the model, forced sparse.
  • TopK SAEs: keep exactly k active latents.
Superposition works because features are rarely active together, so nearly-orthogonal directions rarely interfere. The SAE's job is to find those directions. Watch L0 (active latents per token), explained variance, and dead latents: Lab 5.4 tracks all three on GPT-2.
Steering

Find a feature, then turn it up

$$x \;\leftarrow\; x + \alpha\, d_\text{feature}$$
  • Scaling Monosemanticity (2024): millions of features in a production model, incl. code bugs and deception.
  • Clamping them changes behaviour.
  • Lab 5.4: steer GPT-2 with a forward hook.
Steering adds a direction to the residual stream at every generated position. In the toy, the "bee" latent stays off until α ≈ 1.2 (ReLU threshold), then rises linearly. Caveat: features found by SAEs depend on the dictionary size and sparsity, so treat them as useful hypotheses, not ground truth.
🍯 Key takeaway

Neurons are polysemantic. Sparse directions often aren't, and you can turn them up.

A wide, sparse dictionary pulls features back out of superposition. Adding a feature's direction steers what the model says.
